    "body": "#### Trac ticket number\n\n[ticket-37493](https://code.djangoproject.com/ticket/37493)\n\n#### Branch description\n\nWhen `SeparateDatabaseAndState` executes, `state_forwards` runs on `project_state` before `database_forwards`. Because `StateApps.clone()` reuses Python model classes whose `_meta.apps` references `project_state.apps`, model classes in `from_state` share an apps registry that was already mutated by `state_operations`. If a preceding database operation (e.g. creating an unrelated model or adding a field) resets relation caches via `clear_cache()`, subsequent operations such as `AlterField` re-evaluating relations against `_meta.apps` fail to discover reverse foreign key relations pointing to the old model. Consequently, referencing foreign key columns remain un-altered with their old type in the database schema.\n\nThis PR clears the cached `apps` property (`to_state.__dict__[\"apps\"]`) at the entry of `SeparateDatabaseAndState.database_forwards` and `SeparateDatabaseAndState.database_backwards`. This forces `to_state` to render an isolated `StateApps` registry with accurate relationship trees, matching the behavior of running operations outside `SeparateDatabaseAndState`.     "body": "Supersedes #22305 (which was automatically closed by the triage bot due to the 1-open-PR limit; my previous PR #22301 has now been closed).\n\n### Description\n\nWhen combining querysets (using `.union()`, `.intersection()`, or `.difference()`) of a model that defines `Meta.ordering` on database backends that do not support ordering in compound subqueries (such as SQLite), Django raises a `DatabaseError`:\n\n```python\n# Model with `class Meta: ordering = ['info']`\nqs1 = ExtraInfo.objects.filter(value=1)\nqs2 = ExtraInfo.objects.filter(value=2)\nlist(qs1.union(qs2))\n# DatabaseError: ORDER BY not allowed in subqueries of compound statements.\n```\n\nThe same issue occurs when using `Subquery` with a combined queryset on such models, which previously forced developers to manually add `.order_by()` to clear default ordering on each branch.\n\n### Cause\n\nIn `SQLCompiler.get_combinator_sql()`, compilers for the individual combined queries are inspected for ordering via `compiler.get_order_by()`. Even when the user never called `.order_by()`, the model's default ordering (`Meta.ordering`) was evaluated on the subqueries, triggering `DatabaseError: ORDER BY not allowed in subqueries of compound statements.` when `features.supports_slicing_ordering_in_compound` is `False`.\n\nIn standard SQL set operations, individual branch subqueries should not receive default model ordering unless explicitly requested.\n\n### Solution\n\nIn `get_combinator_sql()`, when a combined subquery does not have explicit ordering (`not query.order_by and not query.extra_order_by`), clone the query and set `default_ordering = False`. \n\nThis ensures that:\n1. Individual compound subqueries do not receive unwanted model default ordering.\n2. Explicit ordering (e.g. `qs1.order_by(...)`) is preserved and continues to trigger validation on unsupported backends as expected.\n3. The outer combined query retains its default ordering on backends that support it.\n\n### Tests\n\n- Added `test_union_with_model_default_ordering` and `test_union_in_subquery_with_model_default_ordering` to `tests/queries/test_qs_combinators.py`.\n- Verified that all 75 tests in `queries.test_qs_combinators` pass.\n- Verified that full `queries` (512 tests) and `expressions` (213 tests) suites pass with no regressions.",
